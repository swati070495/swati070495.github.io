Context

Redesigning a room is hard to picture and harder to shop. Existing tools split the problem in two: image generators make pretty rooms you can't actually buy, and retail catalogs sell products with no design vision. The gap is a tool that does both — produces a redesign with real design taste, and the shoppable products to build it, personalized to a person's style and budget.

Product decisions

Treat output quality as the core product risk.
One off-brand image breaks trust in an AI design tool, so I built a dedicated quality-control stage into the pipeline — the model has to pass its own QC before a result reaches the user. Output consistency across 22 moods and 15 room types was the bar, not raw generation.
Make it shoppable, not just pretty.
The redesign and the commerce are one flow: click-to-shop product cards routed by budget tier across partner retailers. Design vision and "buy it now" live on the same screen.
Gate generation to convert.
Anonymous visitors get one free generation, then sign in for more. The funnel is tuned to turn first-time curiosity into accounts without killing the first taste of the product.
Ground the model in real design taste.
I built a ~339-chunk RAG corpus from design editorial so outputs reflect actual design principles — palette, materials, proportion — instead of generic LLM aesthetics.

How it works — 6-agent RAG pipeline

Retrieval› Vision analysis› Design strategy› Prompt engineering› Image · gpt-image-1› Quality control
RetrievalPulls relevant design references from the pgvector corpus to ground the redesign in real editorial.
Vision analysisReads the uploaded room photo — layout, lighting, existing pieces — to anchor the redesign to the actual space.
Design strategyChooses palette, materials, and mood for the redesign from the retrieved references and the user's chosen style.
Prompt engineeringComposes the image-generation prompt from the strategy and references, so the render is on-brief.
Image generationOpenAI gpt-image-1 renders the photorealistic redesign (upgraded from DALL·E 3 for fidelity).
Quality controlChecks the output stays on-brand and on-spec before it's returned — the trust gate of the whole pipeline.

The MCP server

I built a custom MCP (Model Context Protocol) server that exposes the design knowledge base to an AI agent as five callable tools, so the agent reasons with structured, authoritative domain knowledge instead of guessing.

get_style_guideDetailed info on 10 design styles — materials, palettes, retailers, price anchors, trend notes.
get_design_principlesEight core rules (60-30-10 color, rule of three, focal point, scale, lighting, negative space, texture, traffic flow).
generate_product_queriesBuilds retailer-optimized, budget-aware search queries (specific 5–8 word queries instead of vague 2–4 word ones).
blend_stylesAdvises on mixing two or more styles — shared materials, combined palettes, dominant-vs-accent strategy.
search_design_editorialPoints to results across Dezeen, AD, Elle Decor, Apartment Therapy, House Beautiful.

Context

There's no single source of truth for local animal-volunteering and fostering opportunities — the information is scattered across shelters, each with its own site and format. I scoped the problem from a real user persona and owned it from there: someone who wants to help but can't easily find where, how, or whether they're a fit.

Product decisions

Separate the domain into three agents instead of one.
Data, volunteering, and fostering are distinct intents with distinct logic. Splitting them gave cleaner intent routing and higher accuracy than a single agent trying to do everything — and made each part testable in isolation.
Invest in retrieval quality over breadth.
A wrong match erodes trust fast in a matching product, so I tuned the chunking strategy and added a re-ranking pass to push relevance to 0.95–0.97 rather than chasing a bigger, noisier index.
Build trust and safety guardrails in from the start.
Matching volunteers and foster homes to animals needs rails, not just relevance — so the system enforces a no-show policy and foster-return logic, blocking matches that fail those checks.
Pivot the data source to protect the timeline.
When the Petfinder API was discontinued mid-build, I made the call to pivot to a curated 20-shelter dataset rather than chase a blocked integration — keeping a tested product shipping inside the 48-hour window. Prioritization under a hard constraint.

How it works — 3-agent LangGraph system

Intent routing› Data agent· Volunteering agent· Fostering agent
OrchestratorRoutes each request to the right agent by detected intent (LangGraph manages multi-agent state).
Data agentIngests and serves the shelter dataset — the system's source of truth.
Volunteering agentMatches a person to local volunteering opportunities based on intent and context.
Fostering agentMatches fostering requests, applying the foster-return safety guardrail.
Reasoning + memoryPlan-and-Execute + ReAct + Tree-of-Thoughts reasoning over a CoALA memory framework.
Retrieval88 chunks in Supabase pgvector (256/512-char strategy), text-embedding-3-small, re-ranked with Claude Sonnet.

STRIDE

An autonomous shopping agent that closes the gap between recommending and buying — and can be trusted to spend.

Role
Co-built — I owned the trust & control layer and the user experience
Stack

Status

Built at
Internet of Agents Hackathon (AGI House × Coframe)

Context

AI can recommend products but can't buy them, and most shopping agents are stateless — no memory across sessions, no learning, and no safe way to let them transact. STRIDE is an agent that remembers a user's preferences, learns what works, and completes purchases autonomously within limits the user sets.

My role: STRIDE was co-built at a hackathon. I owned the trust & control layer (permissions and payments) and the onboarding-to-results experience — the parts that make an autonomous spending agent safe and legible. The sections below focus on what I owned, with the wider system described for context.

Product decisions (what I owned)

Make autonomous spending safe by design.
For an agent that spends real money, trust is the product. I designed scoped, non-escalatable permissions set at onboarding — approved sites, spend ceiling, categories — that no agent can override mid-session, plus always-visible Pause / Approve / Override controls.
Pay machine-to-machine, never expose a card.
Payments run agent-to-merchant over the x402 protocol — real USDC transfers on Base Sepolia (EIP-3009) — so a purchase completes without a human card ever entering the loop.
Make the agent legible, not a black box.
I designed the experience so users can see the agent's live reasoning and watch its results improve, rather than trusting a silent process — the observability is what earns the permission to act.

The trust & control layer

Scoped permissions· Pause / Approve / Override· x402 machine-to-machine payments
Auth (permissions)Issues a scoped credential at session start defining exactly what the agent may do — approved sites, spend ceiling, categories. No agent can escalate mid-session.
ControlsAlways-visible Pause / Approve / Override — the human stays in the loop on every autonomous action.
Paymentsx402 HTTP-402 flow: real USDC transfers on Base Sepolia (EIP-3009), settled machine-to-machine and verifiable on-chain, with no card exposed.

The experience I designed

A Streamlit app in three screens: a five-question onboarding that captures the user's preferences and limits; a live run view that streams the agent's reasoning as it works; and a results view that shows what it did and the payment confirmation. The whole flow is built so the user can see, pause, or override at any point.

The wider system (co-built, for context)

Beyond the trust layer, STRIDE runs a multi-agent loop: a memory layer that persists preferences across sessions, a shopping agent that reads live retail pages and reasons over them, a reflexion step that writes plain-English lessons after each run, and a reinforcement-learning loop that converges on the best strategy for each user over a handful of runs.

InterviewIQ

An AI interview-prep platform — role- and JD-tailored mock interviews with structured, STAR-based feedback. This case study is the Phase 1 product definition and system design.

Role

Deliverable

LLM approach
Hosted GPT for Phase 1, with a self-hosting path mapped for later
Status
Phase 1 spec

Context

Interview prep is generic — candidates rehearse canned questions with no tailoring to the role or the specific job, and no structured feedback on how they answered. InterviewIQ generates role- and JD-specific mock interviews and scores each answer against the STAR framework, so practice maps to the job a candidate is actually targeting.

Phase 1 scope

OnboardingMinimal profile (role, industry, experience) with email or Google/LinkedIn OAuth.
Mock interviewLLM generates role/industry-specific questions and chains follow-ups via session memory; a STAR hint sits above each question.
JD "lite" analyzerPaste a job description; the LLM extracts 3–5 core competencies and crafts one tailored question per competency.
Feedback engineA "critic" prompt scores STAR adherence 1–5 and returns top strengths and gaps.
Progress trackerRecent sessions, average score, and an improvement indicator across attempts.

Product decisions

Start hosted, self-host later.
Phase 1 ships on hosted GPT for speed to market; self-hosting is deferred until product–market fit justifies the infra and engineering cost. I mapped the full trade-off across time-to-market, cost, scalability, ops, customization, latency, privacy, and model freshness so the future migration is a deliberate call.
Use RAG to anchor questions in reality.
Instead of zero-shot JD parsing, retrieve similar real-world JDs and the questions companies actually ask — cutting hallucination and surfacing real interview patterns. The same retrieval pattern powers company-specific prep, personalized coaching snippets, resume-augmented prompting, and a resource recommender.
Privacy by design.
Resumes, transcripts, and identifiers are sensitive, so optional data is deferred until opt-in; everything is encrypted in transit (TLS 1.2+) and at rest (AES-256 via KMS), gated by RBAC and least-privilege, with GDPR export/delete rights and retention plus anonymization built in from the start.
Make the build decision economic, not vibes.
I modeled three implementation options with monthly cost ranges at pilot scale, so the architecture choice is grounded in real numbers.

System architecture — the right store for each job

User profilePostgreSQL — ACID transactions, strong schema, joins
AuthSecrets Manager / Vault — encrypted token storage, rotation
Session memoryRedis — low-latency context for live interviews
Interview recordsMongoDB / S3 — flexible transcripts + feedback
Job descriptionsPinecone + Redis cache — semantic retrieval for RAG
AnalyticsClickHouse / BigQuery — score-trend aggregations
Resource libraryS3 + CloudFront — scalable asset delivery

Cost analysis — monthly, at ~1,000 sessions

Option AHosted GPT + serverless — lowest ops, instant autoscaling. ~$974–$1,654/mo.
Option BHosted GPT + dedicated VMs — predictable baseline, more ops. ~$1,122–$1,602/mo.
Option CFully self-hosted GPT — full data control, high fixed cost. ~$3,600–$4,100/mo.
