Existing tools split the problem in two: image generators make pretty rooms you can't actually buy, and retail catalogs sell products with no design vision. The gap is a tool that does both — produces a redesign with real design taste, and the shoppable products to build it, personalized to a person's style and budget. PRODUCT DECISIONS Treat output quality as the core product risk. One off-brand image breaks trust in an AI design tool, so I built a dedicated quality-control stage into the pipeline — the model has to pass its own QC before a result reaches the user. Output consistency across 22 moods and 15 room types was the bar, not raw generation. Make it shoppable, not just pretty. The redesign and the commerce are one flow: click-to-shop product cards routed by budget tier across partner retailers. Design vision and "buy it now" live on the same screen. Gate generation to convert. Anonymous visitors get one free generation, then sign in for more. The funnel is tuned to turn first-time curiosity into accounts without killing the first taste of the product. Ground the model in real design taste. I built a ~339-chunk RAG corpus from design editorial so outputs reflect actual design principles — palette, materials, proportion — instead of generic LLM aesthetics. ROLE Solo — built and pitched as the only PM in the room STACK Flutter (Dart) · GenUI SDK · Featherless AI — Qwen2.5-72B-Instruct · Supabase (PostgreSQL) STATUS Hackathon winner BUILT AT Flutter SF × Very Good Ventures GenUI Hackathon CONTEXT QSR loyalty is one-size-fits-all — every member sees the same static points, offers, and challenges. FlameRewards reimagines a McDonald's-style loyalty app where the experience itself is personalized: instead of fixed screens, a multi-agent system generates each member's quests and challenge cards on the fly, tuned to how they actually order. PRODUCT DECISIONS Personalize the interface, not just the content. Most "personalization" swaps which offer shows inside a fixed layout. The generative-UI bet is bigger: let the model compose the screen itself, which quest, framed how, with what challenge, so the UI adapts to the member instead of the member adapting to the UI. Solve cold start before solving personalization. A new member has no order history to personalize from, so I designed cohort borrowing, using behavior patterns from similar members, as the fallback until the system has enough of their own data to switch to direct collaborative filtering. Never let an LLM call be a single point of failure. This was live and demoed, so every LLM call has a deterministic fallback. If generation fails or times out, the member still gets a coherent, on-brand screen instead of a broken one. Reliability was as much the product as personalization was. Keep the model to two calls per session. A Quest Agent and a Cold Start Agent cover the experience, keeping latency and cost predictable instead of chaining calls per widget. HOW IT WORKS — 5-AGENT SYSTEM Behavior data › Cold Start / Quest Agent › Qwen2.5-72B via Featherless › GenUI SDK › Rendered in Flutter Cold Start Agent Builds a starting experience for new members via cohort borrowing when there's no order history yet. Quest Agent Composes each member's quests and challenges once enough behavioral data exists. Collaborative filtering Reads the behavior_patterns table to match members to relevant quests based on similar members' activity. GenUI SDK Takes the model's output and composes it into a live widget tree from an 8-widget custom catalog, not a static template. Deterministic fallback Wraps every LLM call so a failed or slow generation still renders a coherent screen. I scoped the problem from a real user persona and owned it from there: someone who wants to help but can't easily find where, how, or whether they're a fit. PRODUCT DECISIONS Separate the domain into three agents instead of one. Data, volunteering, and fostering are distinct intents with distinct logic. Splitting them gave cleaner intent routing and higher accuracy than a single agent trying to do everything — and made each part testable in isolation. Invest in retrieval quality over breadth. A wrong match erodes trust fast in a matching product, so I tuned the chunking strategy and added a re-ranking pass to push relevance to 0.95–0.97 rather than chasing a bigger, noisier index. Build trust and safety guardrails in from the start. Matching volunteers and foster homes to animals needs rails, not just relevance — so the system enforces a no-show policy and foster-return logic, blocking matches that fail those checks. Pivot the data source to protect the timeline. When the Petfinder API was discontinued mid-build, I made the call to pivot to a curated 20-shelter dataset rather than chase a blocked integration — keeping a tested product shipping inside the 48-hour window. Prioritization under a hard constraint. ROLE Co-built — I owned the trust & control layer and the user experience STACK Python · x402 / Base Sepolia (USDC) · Claude Sonnet · Streamlit · FastAPI STATUS Working prototype BUILT AT Internet of Agents Hackathon (AGI House × Coframe) CONTEXT AI can recommend products but can't buy them, and most shopping agents are stateless — no memory across sessions, no learning, and no safe way to let them transact. STRIDE is an agent that remembers a user's preferences, learns what works, and completes purchases autonomously within limits the user sets. My role: STRIDE was co-built at a hackathon. I owned the trust & control layer (permissions and payments) and the onboarding-to-results experience — the parts that make an autonomous spending agent safe and legible. The sections below focus on what I owned, with the wider system described for context. PRODUCT DECISIONS (WHAT I OWNED) Make autonomous spending safe by design. For an agent that spends real money, trust is the product. I designed scoped, non-escalatable permissions set at onboarding — approved sites, spend ceiling, categories — that no agent can override mid-session, plus always-visible Pause / Approve / Override controls. Pay machine-to-machine, never expose a card. Payments run agent-to-merchant over the x402 protocol — real USDC transfers on Base Sepolia (EIP-3009) — so a purchase completes without a human card ever entering the loop. Make the agent legible, not a black box. I designed the experience so users can see the agent's live reasoning and watch its results improve, rather than trusting a silent process — the observability is what earns the permission to act. THE TRUST & CONTROL LAYER Scoped permissions · Pause / Approve / Override · x402 machine-to-machine payments Auth (permissions) Issues a scoped credential at session start defining exactly what the agent may do — approved sites, spend ceiling, categories. No agent can escalate mid-session. Controls Always-visible Pause / Approve / Override — the human stays in the loop on every autonomous action. Payments x402 HTTP-402 flow: real USDC transfers on Base Sepolia (EIP-3009), settled machine-to-machine and verifiable on-chain, with no card exposed. THE EXPERIENCE I DESIGNED A Streamlit app in three screens: a five-question onboarding that captures the user's preferences and limits; a live run view that streams the agent's reasoning as it works; and a results view that shows what it did and the payment confirmation. The whole flow is built so the user can see, pause, or override at any point. THE WIDER SYSTEM (CO-BUILT, FOR CONTEXT) Beyond the trust layer, STRIDE runs a multi-agent loop: a memory layer that persists preferences across sessions, a shopping agent that reads live retail pages and reasons over them, a reflexion step that writes plain-English lessons after each run, and a reinforcement-learning loop that converges on the best strategy for each user over a handful of runs. ROLE Co-built — team of two STACK Python · Claude Sonnet (tool_use) · 1Password SDK · FastAPI · HMAC · pytest STATUS Working prototype · 29 tests BUILT AT AGI House × 1Password Agent Identity Hackathon LINKS GitHub ↗ My role: TrustLane was co-built as a team of two with Rohit — we built it together across the agent pipeline, the trust model, and the console. CONTEXT AI agents are starting to book and pay on people's behalf, but the platforms they transact with have no way to know whether an agent is in-scope, uncompromised, and safe to trust with a credential. TrustLane is the B2B trust and identity layer that sits between agents and payments: it scores every agent action and releases a scoped credential only when that action clears. PRODUCT DECISIONS Rule-based scoring, not an LLM judge. The thing deciding whether money can move has to be deterministic and auditable, so trust is scored by explicit signals and weights, not another model. It's safe to run live and every decision can be explained. Score per agent, not one universal score. A read-only search agent and a money-moving payment agent carry very different risk, so each agent type is scored on differently weighted signals — the payment agent is weighted hardest on source trust and budget conformance. Decay trust across delegation hops. The deeper an action is delegated agent-to-agent, the less it should be trusted. Trust decays each hop (1.0 to 0.9 to 0.8 and down) and past a few hops can never auto-approve, modeling the real risk of long delegation chains. Scope credentials to a single use. When an action clears, the released credential is bound to one merchant, one amount, and a 30-second lifetime, and can't be re-delegated. The secret never even loads into memory on a block or review. Least privilege, enforced. HOW IT WORKS — 6-AGENT SYSTEM Orchestrator › Search › Booking › Payment · Delegation · Trust Arbiter Orchestrator Routes tasks to the right sub-agent. Search agent Browses inventory, read-only — lowest scrutiny. Booking agent Reserves listings, requires a credential. Payment agent Moves money, held to the highest scrutiny. Delegation agent Validates HMAC-signed delegation tokens. Trust Arbiter Scores every action and holds final authority to approve, review, or block. THE TRUST MODEL 5 signals Source trust, scope conformance, budget conformance, vendor allowlist, identity validity — weighted per agent type. Hard caps A detected injection forces a review; a missing delegation forces a block — regardless of score. Trust decay Score drops each delegation hop; hop 4+ can never auto-approve. Self-learning reputation Agents earn or lose trust from outcomes (plus on success, minus on error), feeding back as a multiplier. Scoped credentials 1Password-backed: one merchant, one amount, 30-second lifetime, non-delegatable. ROLE Product lead — scope, architecture, data & privacy strategy, cost modeling DELIVERABLE Phase 1 PRD + system design (architecture, data strategy, cost analysis) LLM APPROACH Hosted GPT for Phase 1, with a self-hosting path mapped for later STATUS Phase 1 spec CONTEXT Interview prep is generic — candidates rehearse canned questions with no tailoring to the role or the specific job, and no structured feedback on how they answered. InterviewIQ generates role- and JD-specific mock interviews and scores each answer against the STAR framework, so practice maps to the job a candidate is actually targeting. PHASE 1 SCOPE Onboarding Minimal profile (role, industry, experience) with email or Google/LinkedIn OAuth. Mock interview LLM generates role/industry-specific questions and chains follow-ups via session memory; a STAR hint sits above each question. JD "lite" analyzer Paste a job description; the LLM extracts 3–5 core competencies and crafts one tailored question per competency. Feedback engine A "critic" prompt scores STAR adherence 1–5 and returns top strengths and gaps. Progress tracker Recent sessions, average score, and an improvement indicator across attempts. PRODUCT DECISIONS Start hosted, self-host later. Phase 1 ships on hosted GPT for speed to market; self-hosting is deferred until product–market fit justifies the infra and engineering cost. I mapped the full trade-off across time-to-market, cost, scalability, ops, customization, latency, privacy, and model freshness so the future migration is a deliberate call. Use RAG to anchor questions in reality. Instead of zero-shot JD parsing, retrieve similar real-world JDs and the questions companies actually ask — cutting hallucination and surfacing real interview patterns. The same retrieval pattern powers company-specific prep, personalized coaching snippets, resume-augmented prompting, and a resource recommender. Privacy by design. Resumes, transcripts, and identifiers are sensitive, so optional data is deferred until opt-in; everything is encrypted in transit (TLS 1.2+) and at rest (AES-256 via KMS), gated by RBAC and least-privilege, with GDPR export/delete rights and retention plus anonymization built in from the start. Make the build decision economic, not vibes. I modeled three implementation options with monthly cost ranges at pilot scale, so the architecture choice is grounded in real numbers.
